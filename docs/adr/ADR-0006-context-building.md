# ADR-0006: 上下文构建策略与"角色 vs 全局提示词"关系

> 状态：已接受 · 产出：flow-design-backend（2026-10-12）· 关联：docs/deliverables/chat-mvp/02-后端设计.md §6，解决 01-需求开放问题 #1、#3

## 背景

需求功能 #6（MVP）与 #15–#18（完整版）要求上下文管理"精心设计"：按条数/token 预算截断、旧消息摘要压缩、钉住豁免；同时引入"角色"（系统提示词 + 模型参数）。未定的是：会话没选角色时用什么、角色与全局提示词是否叠加、摘要何时触发与是否缓存。不决策的代价：数据模型与请求构建无法定型，前端也无法确定模型选择器与角色选择器的语义。

## 决策

1. **提示词来源二选一，不叠加**：`conversation.role_id` 有值 → 角色 `systemPrompt` + `params`；为空 → `settings.global_prompt`；全局也空则不发送 system 消息。
2. **构建顺序**：system（角色或全局）→ 摘要 → 钉住消息 → 最近消息（最近的消息优先保留）。
3. **截断两层**：MVP 按条数（默认 20）；完整版改为 token 预算（模型窗口 − 输出预留 − system/摘要开销），估算器用启发式（CJK 1 token/字符、ASCII 1 token/4 字符），允许 10% 误差，不引 tiktoken。
4. **摘要触发与缓存**：被截断的旧消息累积超过 30 条时生成摘要，存入 `conversation_summaries` 并记录 `through_seq`；**按 `through_seq` 缓存复用**，同一区间不重复摘要；摘要失败降级为直接截断，绝不阻塞对话。
5. **钉住豁免**：`pinned` 消息始终包含且不参与截断，但仍计入 token 预算；若钉住内容本身超预算 → `422 context_too_long`。
6. **system prompt 与摘要都不作为可见消息落库**——它们是请求时构建的产物，不污染用户看到的历史（也避免导出文件里出现"摘要"这种内部构造）。

## 权衡

- **角色叠加在全局提示词之上**：放弃——"选了角色还被全局提示词暗中影响"对通用用户不可解释，且调试困难（这也是 01-需求把它列为开放问题的原因）。
- **全局提示词设为必填/默认角色**：放弃——未配置提示词才是多数通用用户的起点，强制选择会增加首用摩擦（与"开箱可用"目标冲突）。
- **完整版一步到位（首次即上 token 预算 + 摘要）**：放弃——MVP 要先把链路跑通，截断策略是纯内部逻辑，可后替换且不动数据库（摘要表用独立迁移 0002 引入）。
- **引 tiktoken 精确计算**：放弃——需要按模型维护编码表、含 cgo/大词表依赖，而验收允许 10% 误差；启发式足够决定"该不该截断"。
- **每次重新摘要（不缓存）**：放弃——重复烧 token 且拖慢响应；`through_seq` 缓存代价极小。
- **把摘要存成一条 `role=system` 消息**：放弃——会出现在导出文件与消息列表里，语义污染。

## 后果

- **正面**：角色语义清晰可解释；摘要表独立迁移使 MVP 可先落地；构建过程可测（纯函数 + 假模型）。
- **负面 / 代价**：启发式估算在某些语言（如 emoji 密集、代码密集）下偏差更大，可能在边界处过早截断；用户从全局提示词切到角色时行为变化明显（需要 UI 提示，属前端文案）。
- **后续跟进**：完整版实测若出现"截断过早导致回答质量下降"，优先调估算系数而非换方案；阶段 2 的工具调用会改上下文构建（工具结果也是上下文），届时回来修订本节顺序。
