# ADR-0004: 本地存储选 SQLite（纯 Go 驱动 + WAL + 单连接池）

> 状态：已接受 · 产出：flow-design-backend（2026-10-12）· 关联：docs/deliverables/x-gulu/02-后端设计.md §2 §4

## 背景

需求明确"数据存本地 SQLite、重启不丢"。开源个人工具的实际交付形态是"用户拿到一个可执行文件就能跑"——若依赖 cgo，交叉编译与用户本地构建的门槛都会上升（目标用户含不写代码者）。并发方面：流式写入 + 会话读取 + 用户改配置会同时发生（需求边界 #8：改配置不得打断进行中的对话）。

## 决策

- 数据库 **SQLite**，驱动用 **`modernc.org/sqlite`**（纯 Go，无 cgo）。
- 连接参数：**WAL** 模式 + `busy_timeout=5000ms` + `foreign_keys=ON` + **`MaxOpenConns(1)`**。
- 迁移：内嵌 `migrations/NNNN_*.sql` + `PRAGMA user_version` 自研执行（约 20 行），不引迁移库。
- 消息**一条一行**、`UNIQUE(conversation_id, seq)`；流式增量更新同一行。

## 权衡

- **`mattn/go-sqlite3`（cgo）**：生态最成熟，放弃——cgo 使 `GOOS/GOARCH` 交叉编译复杂化，与"单文件交付"冲突。
- **PostgreSQL/MySQL**：放弃——需要用户另外安装服务，与"个人工具、无登录、开箱即用"直接矛盾。
- **纯文件（JSON/JSONL）**：最简单，放弃——会话列表排序、全文搜索（完整版）、级联删除、并发写都需要自己实现一遍，final 收益为负。
- **连接池放开多读**：性能略好，放弃——`MaxOpenConns(1)` 在本机单用户负载下无感知差异，却消除一整类 `SQLITE_BUSY` 心智与调试成本。
- **引入迁移框架（goose/migrate）**：放弃——本项目迁移量极小，多一个间接层不如 20 行自研 + 内嵌文件可审计。

## 后果

- **正面**：`CGO_ENABLED=0` 即可产出各平台单文件二进制；数据就是一个 `xgulu.db` 文件，备份/迁移即复制文件（对通用用户友好）；写串行天然避免了并发写冲突。
- **负面 / 代价**：需自行保证迁移脚本"只用 SQLite 支持的特性"；单连接池下若将来出现长事务会阻塞一切写入（当前所有事务均为毫秒级）。
- **后续跟进**：完整版的全文搜索先用 `LIKE`（数据量为个人规模），若实测慢再评估 FTS5 虚表；届时新迁移文件而非改老文件。
