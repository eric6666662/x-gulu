# ADR-0002: 状态管理采用 Pinia 双业务 store + 局部状态兜底

> 状态：已接受 · 产出：flow-design-frontend（2026-10-12）· 关联：docs/deliverables/x-gulu/02-前端设计.md §3

## 背景

聊天应用里存在两类必须跨组件共享的数据：**流式状态**（streaming/interrupted/error，同时被 Composer、MessageList、状态栏消费）与**配置数据**（服务商/角色/全局设置，设置页写、聊天页读）。同时纪律要求"单页工具不上全局状态管理"——需要界定共享与局部的边界。不决策的代价：流式状态被提升到错误层级（如每个组件自己开流）导致状态分叉。

## 决策

Pinia 三个 store：`chat`（会话/消息/流式状态）、`settings`（服务商/角色/全局配置）、`toast`（极小反馈队列）；其余一切状态（模态开关、输入框内容、下拉展开、滚动位置）一律组件本地。不引入服务端缓存类方案（TanStack Query 等）。

## 权衡

- **纯组件本地 + provide/inject**：流式状态要跨三个兄弟组件，inject 的更新链路与测试都更绕，放弃。
- **TanStack Query / 组合式请求缓存**：能做服务端状态缓存，放弃——本项目接口少、无分页失效复杂度，SSE 流不是"请求缓存"形状；引入会带来 stale-heap 等额外心智。
- **单一大 store**：省事，放弃——settings 与 chat 生命周期不同（settings 全局常驻、chat 随会话切换），合并会模糊边界。
- **全局 EventBus**：放弃——隐式依赖不可测试，违背"深模块小接口"。

## 后果

- **正面**：共享状态的来源唯一；组件测试可直接注入 store；放弃缓存库使依赖面保持最小。
- **负面 / 代价**：会话列表等服务端数据需手动维护副本与乐观更新回滚（已在 `stores/chat` actions 内封装）。
- **后续跟进**：若阶段 2/3 出现复杂服务端状态缓存需求，重新评估请求缓存方案（本决策可逆，成本是 store 内手写逻辑的迁移）。
