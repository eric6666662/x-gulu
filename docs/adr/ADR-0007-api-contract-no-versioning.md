# ADR-0007: API 契约不做版本号，错误码全量显式定义

> 状态：已接受 · 产出：flow-design-backend（2026-10-12）· 关联：docs/deliverables/chat-mvp/02-后端设计.md §1

## 背景

前后端同仓、同二进制发布（前端 `embed` 进 Go 二进制），消费者只有自家前端；但需求边界要求"每条错误路径都有可读行为"（01-需求 §边界与异常 11 条），前端要为每种失败写文案。需要定：路径是否带版本、错误形状是否统一。

## 决策

1. API 前缀固定 `/api`，**不带 `/v1` 版本段**；破坏性变更与前端同发布完成。
2. **统一错误体**：`{"error":{"code":"...","message":"...","field":"..."?}}`，`code` 为稳定机器标识，`message` 为去行话中文、可直出界面。
3. **错误码全量显式定义**（02-后端设计 §1.4 的表）：400/401/404/409/422/429/500/502/504 每类都有明确语义与中文文案，禁止"只有 200 和 500"。
4. SSE 流内的错误也走同一 `code` 词表（事件 `error`），与 HTTP 错误码共用一份常量定义。

## 权衡

- **`/api/v1` 版本段**：放弃——没有第三方消费者，版本段只会带来"哪个版本是真身"的长期困惑；真需要兼容时，本地单机场景下直接改前端更省。
- **HTTP 状态码即全部语义（不加 body code）**：放弃——前端需要区分 `invalid_api_key`（引导改 key）与 `rate_limited`（提示稍后重试）这类同状态码不同动作的情况。
- **错误 message 由前端按 code 翻译**：放弃——文案需与后端错误上下文（如 token 超限的具体数字）耦合，前端翻译会丢信息；且错误口径统一在后端更易保持"去行话"。
- **直接透传上游错误体**：放弃——可能泄露上游细节/英文行话，且违反"不记录、不外泄上游响应体"的隐私约定。

## 后果

- **正面**：前端错误态可枚举、可测试；文案单点维护（面向通用用户）；错误码表成为前后端共同词表。
- **负面 / 代价**：破坏性变更无处"平滑过渡"，必须前后端同发布（对单二进制形态无实际代价）；错误码表需随功能增长维护，漏定义会退化成 `internal_error`。
- **后续跟进**：错误码表放在 Go 常量与前端类型定义两处，需在开发阶段加一条测试/脚本校验一致性（`flow-dev` 落地）。
