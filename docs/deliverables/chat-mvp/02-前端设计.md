## 1. 技术栈

| 类别 | 选型 | 理由 |
|------|------|------|
| 框架 | **Vue 3**（`<script setup>` + Composition API）+ TypeScript | 用户拍板（三候选中选 Vue 3） |
| 构建 | **Vite** | 与 Vue 官方同构、开发体验、Vitest 同源 |
| 路由 | **Vue Router 4** | 官方标配，仅 2 条路由也用它（书签/刷新可恢复） |
| 状态 | **Pinia**（官方后继者）→ 详见第 3 节与 ADR-0002 | 流式状态与跨路由数据必须共享 |
| UI 组件 | **自研组件 + 无样式底座 Reka UI**（Radix 的 Vue 移植） | 用户拍板"轻依赖"：视觉完全贴合 02-ui设计/设计稿；Reka 只提供无障碍细节（焦点陷阱、Esc、键盘导航），不带视觉 |
| Markdown | **markdown-it**（`html: false`）+ **highlight.js** | 需求功能 #8；禁 raw HTML 从渲染层防 XSS；hljs 覆盖代码高亮，不引 shiki（体积/异步复杂度不值） |
| 测试 | **Vitest + @testing-library/vue** | 用户拍板；与 Vite 零配置同构 |
| 样式 | **原生 CSS + CSS 变量（设计 token）**，组件用 `<style scoped>` | 设计稿 token 直接落成 `:root` 变量；不引 Tailwind/CSS-in-JS，避免与"轻依赖"冲突 |

新增依赖清单（均已说明理由）：`vue` `vue-router` `pinia` `reka-ui` `markdown-it` `highlight.js`（+ dev：`vitest` `@testing-library/vue` `jsdom` `@types/markdown-it`）。

## 2. 模块划分（深模块）

边界优先按 UI 设计的组件层级与业务域切；"最常变化的东西被隔离"是检验标准。

### 基础设施层

| 模块 | 对外接口（小） | 隐藏的行为 | 边界依据 |
|------|----------------|------------|----------|
| `api/client` | `request<T>(method, path, body?): Promise<T>`<br>`streamChat(path, body, handlers): AbortHandle` | baseURL 拼接、JSON 编解码、`ApiError` 归一化（status/code/message）、SSE 字节流解析（`TextDecoder` 增量解码防多字节截断、`data:` 行拼接、跨 chunk 半行缓冲）、AbortController 生命周期 | 所有网络细节只此一处；协议变（SSE→WS）只改这里 |

## 3. 状态管理

**方案：Pinia 两个业务 store + 一个极小 toast store + 组件本地状态兜底。**

理由（数据形状决定方案，非流行度）：

1. `stream`（流式状态）同时被 **Composer**（停止按钮）、**MessageList**（光标/追加）、**ChatTopBar/状态栏**（"生成中 •••"）消费——跨兄弟组件必须共享，局部状态做不到。
2. `settings`/`services` 在 **设置页写、聊天页读**（引导分流、模型选择器）——跨路由共享。
3. 反面：模态开关、textarea 内容、下拉展开等一律组件本地——单页工具不上全局（纪律）。
4. 放弃 TanStack Query 类方案：本项目接口少、无分页缓存失效复杂度，SSE 流式也不是"请求缓存"形状（ADR-0002）。

## 4. 路由

无登录 → **无鉴权边界**（安全性由后端 127.0.0.1 监听承担，见需求约束）。

| 路由 | 页面 | 鉴权要求 |
|------|------|----------|
| `/` | `ChatShell`：重定向到最近打开的会话；无会话则新建空会话 | 无 |
| `/c/:id` | `ChatShell`（会话视图），`stores/chat.open(id)` | 无 |
| `/settings` | `ChatShell` 主区切 `SettingsView`（侧栏保留，对应 02-ui设计） | 无 |
| `*` | 重定向 `/` | 无 |

刷新可恢复：会话 id 在 URL（`/c/:id`）；服务商/设置进 Pinia 时由 `loadServices()/loadSettings()` 拉取。

| `GET /api/export/all?format=json` | → JSON 文件下载 | 同上 | 已对齐 |

| `PATCH /api/messages/{mid}` | `{pinned}` | 完整版 | 已对齐 |
| `GET /api/search?q=` | `[{conversationId, title, snippet, messageId}]` | 完整版；空结果空态文案 | 已对齐 |

**提议的 SSE 流协议**（`Content-Type: text/event-stream`，POST + fetch 读流）：

```
event: start       data: {"messageId":"msg_...","conversationId":"cnv_...","seq":8}
event: delta       data: {"text":"增量文本"}
event: done        data: {"finishReason":"stop","usage":{"promptTokens":812,"completionTokens":233}}
event: error       data: {"code":"upstream_timeout","message":"模型响应超时，请重试"}
event: interrupted data: {}          （服务端检测到上游中断时；前端本地 stop 则直接收口，不依赖此事件）
```

- `start` 必在首个 `delta` 前到达——前端据此拿到占位消息 id 再渲染流式光标；服务端每 15s 发 `: ping` 保持连接。
- 同会话已有进行中的流 → HTTP `409 stream_in_progress`（前端提示"该会话正在生成回答"）。

- 前端 `streamChat` 返回 `AbortHandle{abort()}`；`abort()` = 需求"停止生成"（保留已生成部分 + 标注已中断）。
- `error` 事件带**已去行话的中文 message**（通用用户受众），前端直接展示，不二次翻译。

## 6. 数据流

以 `/c/:id` 打开会话并发送消息为例：

```
路由 /c/:id
  → ChatShell 挂载
  → stores/chat.open(id)                    [Pinia chat]
      → api/endpoints.getConversation(id)   [api/endpoints]
          → request()（含错误归一）           [api/client]
  → MessageList 渲染 messages                [组件层]
      → 每条经 markdown/render()             [markdown/render]
用户输入 Enter
  → Composer emit send                      [组件层]
  → chat.send(text)：乐观追加用户消息 → stream.status=streaming
      → api/endpoints.postMessage() → streamChat()  [api/client]
          ← SSE delta → chat 累积 → MessageList 增量渲染（光标跟随）
      ← done → status=idle，动作浮现
      ← error → status=error，MessageRow 错误块 + 重试
用户点停止
  → Composer emit stop → chat.stop() → AbortHandle.abort()
      → status=interrupted，保留部分内容（01 边界 #3）
自动滚底
  → MessageList 内 useAutoScroll 订阅内容高度 → 用户上滚则挂起，出现「回到底部」
```

设置页回写：`ServiceFormModal 保存 → stores/settings.saveService() → GET /api/services 刷新 → 聊天页引导分流读 settings.services.length`。
